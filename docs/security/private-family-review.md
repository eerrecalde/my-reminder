# Focused security review for private family distribution

Reviewed 26 November 2026 against commit `591ade4`, the checked-in npm lockfile and Android source. This is a targeted source and configuration review, not a penetration test or a guarantee of security. It did not inspect all third-party source, scan Gradle/Maven artifacts for vulnerabilities, monitor runtime network traffic, test malicious apps, or verify a freshly signed release APK. Repeat the dependency checks and inspect the actual release artifact before distribution.

## Findings and decisions

- **Notification privacy — defer a product change.** `ReminderScheduler.notifyOccurrence` puts the reminder name in the notification title and, for a medicine, its instructions in the body. Android's lock-screen and notification settings determine whether those details are shown; the app does not generally make notification contents private. The Alarm screen itself uses generic content while locked (see `AlarmActivity` and ADR 0001), but that does not make the notification generic. A person who needs privacy should configure Android to hide sensitive notifications or avoid sensitive text. Consider a private-notification option in a separate product decision; changing alert content here could affect usefulness and existing behaviour.
- **Local data and loss — defer encryption and backup design.** `MedicineRepository` uses an app-private SQLite database for reminders, schedules and history; language and sound preferences use private preferences. No application-level encryption was found. Android's app sandbox is the main boundary; an unlocked device, compromised OS, privileged access or a person with access to the app can expose data. `allowBackup=false` reduces routine backup exposure but there is no supported restore or transfer: uninstalling or losing the device can lose records. Use a device lock and restrict device access. Encryption and a recovery mechanism need separate design, including key management and migration.
- **Exported recovery receiver — defer hardening pending platform testing.** `RecoveryReceiver` is exported for system recovery broadcasts and accepts only six listed actions before rebuilding schedules. An explicit intent from another app may still reach an exported receiver; action filtering alone does not authenticate its sender. Repeated accepted broadcasts could trigger work and affect availability. No access to reminder contents or arbitrary outcome mutation was identified through this handler. Assess protected broadcast behaviour across supported Android versions and test any restriction against boot, unlock, clock, package-update and exact-alarm recovery before changing it. The existing bounded recovery work is also tracked in issue 13.
- **Network permission — defer removal pending release validation.** The main manifest grants `INTERNET`; a search of app-owned TypeScript and Kotlin found no app network requests, analytics or logging endpoints. This is not proof that dependencies cannot communicate. The inspected merged release manifest has `usesCleartextTraffic=false`; the React Native Gradle plugin enables cleartext for debug. The permission still permits HTTPS in release. Evaluate removing it with a release build and real reminder flows in a focused follow-up; keep debug Metro requirements in mind.
- **Dependency advisory — defer a focused tooling update.** `npm audit --json` on the lockfile reported six moderate affected package entries, zero high/critical, from one underlying [minimatch denial-of-service advisory](https://github.com/advisories/GHSA-g3hv-75wg-m249): locked `minimatch` 10.2.6 is reached through `@typescript-eslint/typescript-estree` 8.72.1 and the React Native ESLint configuration. These are development dependencies; the finding concerns processing adversarial glob patterns during tooling, not a demonstrated phone-runtime exploit. Audit reports a fix available. Update the compatible lint dependency chain or lockfile in a separate change, inspect the exact resolution and rerun lint, typecheck and tests. Avoid processing untrusted patterns in the meantime. Audit is point-in-time, covers npm advisories only and is not a complete vulnerability assessment.
- **Android dependency advisories — assessment deferred.** The app includes React Native Android/Hermes, AndroidX and transitive Maven artifacts; their vulnerability status was not established by npm audit. A vulnerable native dependency could affect the distributed app even when npm audit reports no runtime finding. Before distribution, generate the resolved release runtime dependency graph, check its versions against an appropriate advisory database, investigate applicable findings and record fixes or explicit risk decisions. Recheck after dependency changes; this remains an open release review item.

## Evidence and other boundaries

- `android/app/src/main/AndroidManifest.xml` requests vibration, foreground media playback, notifications, full-screen intent, exact alarms and boot completion for reminder delivery, plus Internet as above. It does not request contacts, location, camera or storage permissions. Inspect permissions of the actual release manifest again after dependency changes.
- The locally existing merged release manifest was inspected, but its freshness and identity with a distributed APK were not established. It includes the exported launcher and recovery receiver, an unexported AndroidX startup provider and an exported AndroidX profile installer receiver protected by `android.permission.DUMP`. App alarm, outcome, snooze, watchdog, transition and reconciliation receivers, sound service and Alarm activity are unexported. AndroidX adds a signature-protected dynamic-receiver permission. `ReminderScheduler` and `AlarmSoundService` use explicit immutable pending intents. See Android's guidance on [exported components](https://developer.android.com/privacy-and-security/risks/android-exported) and [pending intents](https://developer.android.com/privacy-and-security/risks/pending-intent).
- Searching app-owned `src` and Android main Kotlin for `Log.`, `console.`, `println`, `printStackTrace`, URLs and `fetch` found no logging or network calls. This does not cover dependency or OS logs, crash dumps, or every possible indirect call. No runtime log capture was performed.
- Private distribution and signing instructions in `README.md` require an external release key, backup, APK certificate verification and same-key updates. The debug key is public and must not be used for family releases. This review did not inspect credentials or verify a release certificate.

## Gradle and follow-up

With the documented JDK 17 and SDK, `:app:testDebugUnitTest :app:assembleDebug --warning-mode all` succeeded on Gradle 9.4.1 / AGP 9.2.1 (many tasks were up to date). The warnings include project `android/app/build.gradle` Groovy property assignment syntax (`ndkVersion`, `namespace`, `signingConfig`) scheduled for removal in Gradle 10; equivalent warnings also appear in dependencies. AGP warns that `android.builtInKotlin=false`, `android.newDsl=false` and legacy variant APIs will be removed in AGP 10; the exact callers of the variant APIs were not traced. These are compatibility warnings, not identified vulnerabilities. Before a Gradle/AGP major upgrade, update project syntax, trace plugin callers with `-Pandroid.debug.obsoleteApi=true`, and check compatible React Native and native library versions in a focused upgrade with full Android verification. No bulk dependency upgrade was made here.
